# Signing keys (RL-010 standard)

Each member's **public** approval-signing key lives here as `<name>.asc`. The private keys never do — and never touch the harness.

The standard is a **hardware token** (below). The commands here generate the
**software fallback** key — each member, **by hand, in a plain terminal, never via
an agent session** — for use only until a token is present:

```sh
gpg --full-generate-key          # ECC (sign only) → Curve 25519; real passphrase typed at the pinentry
gpg --list-secret-keys --keyid-format long   # find YOUR_KEYID
gpg --armor --export YOUR_KEYID > docs/keys/<name>.asc
git add docs/keys/<name>.asc && git commit -m "Add <seat> public key" && git push
```

The RL-010 standard, in full (amended — see the charter's Decision 0017):
- **Hardware-resident and non-exportable by construction** — a CCID OpenPGP card / security token. The private half cannot leave the token, so the harness can never hold it; only the **public** half is registered here. "The agent cannot produce this signature" becomes a property of physics, not procedure.
- **A physical user gesture (a touch) per signature**, which no process can forge. A PIN cache is fine; a *gesture* cache is not — one touch per approval.
- Generated **on-device by the accountable person**, never by an agent, and a **different key** (not a subkey of the same primary) from the one backing `pass`/age secret decryption.

**Fallback, until a token is present:** the original interactive software ceremony — generated by hand in a plain terminal (the commands above), passphrase never in a file/env/script/`pass` store, no long-lived `gpg-agent` caching on any agent-slot box (`default-cache-ttl`/`max-cache-ttl` ≤ 300 s). Every ledger row a fallback key signs must record its `mechanism` as **fallback (RL-010-non-compliant)**, so the weaker gesture never passes for the standard.

A gate an agent can satisfy is not a gate. The whole approval structure (RL-003) reduces to "the agent cannot produce this signature" — the token makes that true by construction, and the marked fallback makes it true by discipline while announcing that it is the weaker proof.

## The demo key in this reference ledger

`reviewer.asc` is a **demo** public key — "Rex Reviewer (dx reference ledger DEMO
key — not for real approvals)". It exists so `dx merge` can be run end-to-end by
anyone. It is **not** an RL-010 key and nothing above was followed in making it:
it was generated non-interactively, unprotected, by a script — the opposite of the standard *and* of its marked software fallback. Under the amended RL-010 (charter Decision 0017), a demo or CI key is a **test double**: a fallback that must be structurally incapable of entering a real ledger row.

Its private half was never committed and no longer exists — it was destroyed with
the temporary keyring that made it. That is deliberate. A reference
implementation that shipped a private signing key would contradict this document
in the very directory the document governs, and "the agent cannot produce this
signature" is the whole load-bearing claim of RL-003.

Verification never needs the private half. If you extend the ledger and need to
re-sign, `tools/new_demo_approval.sh` generates a fresh demo key of your own,
registers its public half here, and signs the current head.
